Step 1 of 4

Hashing: from key to bucket

The kernel says“A hash table stores keys in an array of m buckets, and a hash function turns each key into a bucket index: index = key mod m”
Kernel check. Accurate for integer keys with the division method. Real tables use stronger hash functions (and convert strings to numbers first); a prime m spreads keys more evenly.
  • The table is an array of m buckets, numbered 0 to m − 1.
  • The hash function here is index = key mod m: the remainder after dividing by m. It always gives a number from 0 to m − 1.
  • Computing the index takes one step however many keys are stored. That is why hash tables are fast.

Step 2 of 4

Collisions and chaining

The kernel says“Two different keys can land in the same bucket, which is a collision; with chaining each bucket keeps a linked list of its keys”
Kernel check. Accurate. Chaining is one way to handle collisions; open addressing (probing for the next free slot) is the other.
  • A collision happens when two different keys get the same index: 10 and 31 both give 3 with m = 7.
  • With chaining each bucket holds a linked list. A new key is appended to the end of its bucket's chain after checking it isn't already there.
  • Resizing is switched off on this step so the collisions stay visible.

Step 3 of 4

Looking a key up: one bucket, one short walk

The kernel says“To look up a key, compute its index and walk only that bucket's chain, comparing keys until a match or NULL”
Kernel check. Accurate. Average cost is about 1 + n/m comparisons; the worst case, when every key lands in one bucket, is n.
  • To find a key, compute its index, then walk only that bucket's chain, comparing keys.
  • The walk stops at a match (found) or at NULL (not in the table). Other buckets are never touched.
  • Comparisons = position in the chain, so short chains mean fast lookups.

Step 4 of 4

Load factor and resizing

The kernel says“The load factor n / m measures how full the table is; when it passes a limit such as 0.75 the table is resized (m doubled) and every key is rehashed”
Kernel check. Accurate. 0.75 is a common limit (Java's HashMap uses it). Resizing costs O(n) once, but spread over many inserts it averages O(1) each.
  • The load factor α = n / m is the average chain length.
  • When α goes over the limit (here 0.75), the table resizes: m doubles and every key is rehashed with the new m, so most keys move.
  • A resize is expensive once, but it keeps chains short for all later lookups.
